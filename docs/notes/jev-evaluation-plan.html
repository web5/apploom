Jev 验证方案：它是什么、对 web_system 有什么用、怎么验证

Jev 是 TypeSafe AI 的 System One 模型，返回结构化决策而不是文本。本文先说明它的定位和接口，再结合 web_system 的实际代码列出可能的落点，最后给出一套可以自己动手执行的验证步骤。官方数据均为厂商自述，文中标出了哪些我核对过、哪些没有。

一、结论摘要

  • 定位：它是决策层，不是对话模型。适合分类、打分、是非判断，不能做翻译、写作、多步规划。
  • 最大卖点是「带概率的结构化输出」：可以设阈值，高置信度自动执行，低置信度转人工。但文档没有给校准证据，这是要你自己验证的核心。
  • 验证顺序：先拿 key，再做 30 分钟冒烟，再用现成数据做两个对比实验，最后重点看置信度是否可信。
  • 面试前只做冒烟就够。实验放到面试之后。

二、Jev 是什么

项内容来源与可信度
公司与产品TypeSafe AI（旧金山）。Jev 是首个公开的 System One 模型，2026-09-15 起开放早期访问官网、官方博客；日期来自二手报道
输入一段 state（文本或 JSON）加一组带类型的问题官方文档
输出每个问题返回类型化答案和概率，不生成字符串官方文档
三种问题choice 多选一（最多 255 个选项）、score 有序打分、noul 是非概率官方文档
接口POST https://api.typesafe.ai/v1/systemone，Bearer 认证，模型名 jev-latest官方快速开始
SDKPython typesafe-sdk（3.10+），JS/TS @typesafe-ai/sdk（Node 20+）官方快速开始
速度与成本官网称比 LLM 快 193.6 倍、便宜 444.6 倍；输入每十亿 token 42 美元厂商自述 无第三方实测
「零幻觉」输出一定落在你给的选项里。这不等于选对需自行验证
开放程度等待名单，闭源权重，不能自托管官网、二手报道
中文支持文档没有说明，示例全是英文未知
限流、错误码、输入长度快速开始与 Choice 页都没写未知

官方博客自己承认的局限：不支持图像（目前）、选项数上限 255（更多会两阶段，变慢）、速度评测主要在西海岸笔记本上跑、价格可能有补贴、工作流评测的参考答案取自 OpenAI 与 Anthropic 模型的平均值。

置信度是怎么算的

  • choice：(最高概率 − 1/n) / (1 − 1/n)，概率集中为 1，均匀分散为 0。
  • score：按有序档位计算概率加权的平均距离，再与均匀分布比较，下限为 0。
  • noul：不返回置信度，概率值 p 本身就是不确定性。
  • 要点：它只是概率分布的汇总统计量。文档没有校准曲线、ECE 等指标，也没有保证「置信度高就一定准」，只建议用自己的数据调阈值。

三、对 web_system 的可能落点

依据：读过 intent-classifier.ts、deploy.controller.ts、部署 Agent 与 llm-bench 的 RAG 练习。内容中心一项只看到提交标题，未读代码。

位置现状Jev 可能带来的价值要警惕
意图路由LLM 输出 JSON 并自报置信度，「没把握就兜底」只是提示词里的一句话。曾因 maxTokens=60 加 thinking 导致空输出，100% 走兜底多选一直接给各选项概率，不会空输出或被截断；阈值基于概率而不是模型自报中文准确率未知；路由选项变化时要同步改 criteria
部署 prod 确认门服务端只校验 confirm !== true，校验不了用户是否真的同意多一道判断「用户是否明确同意发布到生产」要专门测提示词注入，不能作为唯一防线
内容中心打标与筛选规则加 LLM（来自提交标题）高频分类和相关性打分，成本差距在这类场景最有意义未读代码，价值待确认
RAG 拒答练习 4 用检索得分阈值判断改成「证据是否足以回答」的是非判断，与阈值法对比BM25 的 AUC 已经很高，Jev 不一定更好
轨迹评测的「宣称成功」关键词启发式，有误判对最终回复问一个是非题评测里引入另一个模型，要说明其可信度

不适合的地方

  • 翻译、写作、总结、代码：它不生成文本。
  • agent-core 的主对话与多步工具调用：它不做规划。
  • 接入形态不同：web_system 的模型字典 llm_models 和客户端抽象是聊天补全形态，Jev 是「问题加类型化答案」，要新增一种决策端口，不能直接加进字典。

四、动手验证步骤

步骤 0：拿到访问权限

  • 登录 console.typesafe.ai，在 /keys 获取 API key，设为环境变量 TYPESAFE_API_KEY。
  • 如果仍在等待名单，通过官网 Contact 页申请，拿到之前后面都做不了。

步骤 1：30 分钟冒烟（不写项目代码）

下面的中文路由例子是我按官方请求格式改写的，请求结构与文档一致，内容为我自己编写。

curl --fail-with-body -s https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "Content-Type: application/json" \
  --data-binary '{
    "state": "帮我把 admin 模块发布到 dev 环境",
    "model": "jev-latest",
    "questions": {
      "agent": {
        "type": "choice",
        "instructions": "这句话应该交给哪个助手",
        "criteria": {
          "deploy": "发布、回滚、灰度、查询版本",
          "dev": "读写代码、跑命令",
          "general": "以上都不是或无法判断"
        }
      },
      "is_prod": {
        "type": "noul",
        "instructions": "用户明确要求操作生产环境"
      }
    }
  }'

返回里应有每个选项的 probabilities、confidence 和 usage。冒烟检查清单：

  • 中文是否正常工作；换成英文选项名再试一次做对照。
  • 把「发布到 prod」「发布到 dev」「应该可以吧」「先别发」各试几次，看概率怎么变。
  • 同一输入连跑 5 次，概率是否稳定。
  • 记录单次延迟和 usage。
  • 故意给一个选项列表覆盖不到的输入，看加 other 选项后的表现。
  • 记录遇到的限流和错误码，文档没写，要自己补。

预期BM25 的 AUC 已经很高，Jev 不一定赢；赢不赢都是有价值的结论最能体现「不空输出、概率可控」的优势

步骤 3：校准验证（这是核心）

  1. 可靠性表：按置信度分桶（例如 0–0.5、0.5–0.9、0.9 以上），统计每个桶的实际准确率。置信度 0.9 的预测是否真有约 90% 命中。
  2. 选择性预测曲线：把阈值从低调到高，记录「自动处理的比例」和「这部分的准确率」。直接回答「能不能自动执行、低置信度转人工」。
  3. 高置信度错误清单：对放行类决策单独统计高置信度下的错误，这是最危险的一类。
  4. 稳定性：相同输入重复调用，概率的波动范围。
  5. 语言对照：中文与英文 criteria 的准确率差。

五、约束与风险

  • 只发脱敏数据。这是海外 API，web_system 有面向小程序用户的业务，不要发送真实用户会话。可以用 llm-bench 里已脱敏的语料和问答集。
  • 别把它当唯一防线。部署确认这类高风险判断，只能作为多一道检查。
  • 厂商数据不可直接引用。「快 193 倍、便宜 444 倍」「零幻觉」都是自述，写进汇报前要用自己的数据替换。
  • 早期访问的稳定性、SLA、公司持续性没有信息。评估价值时要把迁移成本算进去。

成本估算（只基于官网标价）：文档示例一次请求约 428 个输入 token、73 个输出 token。按每十亿输入 token 42 美元，一次约 0.00002 美元，1000 次约 2 美分。输出价格没有公开，所以这只是下限估算。
