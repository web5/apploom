web_system 的 Agent 可观测现状：做了什么，没做什么

结论基于对 agent-core、ai-service、ai-agent、gateway 和 admin 前端代码的只读核对。没有连线上库，没有运行 admin 页面，所以「数据实际长什么样」没有验证。重点是区分「设计了」「代码里有」「真的接上了」三种状态。

一、结论摘要

  • 实际在用的可观测是「运行记录」模式：每次 run 的完整步骤流写入 agent_runs 表，再按天聚合到 run_metrics，admin 里有运行列表、详情回放和观测台。
  • 能回答的：某个 Agent 的成功率、耗时、token、成本趋势；某次对话完整发生了什么；为什么路由到这个 Agent（via 归因）。
  • 回答不了的：工具级失败率与延迟、单次模型调用的耗时与 finish_reason、缓存命中、回答质量、跨服务链路追踪。
最需要注意的一点 TelemetryPort（对齐 OTel GenAI 的 llm、tool、run 事件）在引擎里设计并发出了事件，但两个宿主服务构造引擎时都没有注入它，所以这些事件目前没有任何消费方。面试里不能把它说成「已经在用的遥测」。

二、数据是怎么流动的

1. 引擎事件流SSE 事件：intent、tool_call、tool_result、final、error 等
→
2. 控制器收集边推给前端，边把事件收集成 steps
→
3. 落库ai-service 直接写；ai-agent 通过内部 HTTP 推送过去
→
4. 两张表agent_runs 明细；run_metrics 日聚合
→
5. admin运行列表、详情回放、观测台

依据：agent.controller.ts（ai-service 与 ai-agent 各一个）、agent-run-pusher.ts、agent-log.service.ts。

五、发现的问题与风险

#问题依据影响
1遥测端口没有接线见第三节llm、tool 级的指标全部缺失，设计和实际脱节
2ai-service 本地路径的 run 记录可能没有 token 和成本ai-service 控制器收集步骤时只复制 type、name、content、step、ts，没有复制 usage；而成本核算是从步骤里的 usage 提取的。ai-agent 的控制器复制了 usagestudy-assistant、变变等本地 Agent 的观测台可能显示 token 为空、成本为 0。这是按代码推断，没有查库验证
3错误码没有结构化错误码拼在 error 文本前缀无法直接按错误类型聚合
4没有质量归因字段outcome、fail_stage 无命中；内容中心的质量枚举注释提到「与 agent_runs 的 outcome / fail_stage 方法论同构」，但 agent_runs 本身没有只能知道「跑通没」，不知道「对不对」
5每次 run 复制 systemPrompt 全文和用户输入原文agent-run.entity.ts存储增长快；用户输入含个人信息，需要保留期与脱敏策略。我没有看到清理策略
6写入失败静默两处都是只打 warn 或 error 日志、不抛错推送失败时运行记录直接丢失，没有告警或补偿，指标会偏低
7成本口径不完整没有单价记 0 而不是「未知」；不含缓存折扣成本可能被低估，且无法区分「免费」和「没定价」
8ai-service 记录了全部事件，包括每个内容增量ai-service 控制器对所有事件一律收集（包括 content_delta、reasoning_delta），而 ai-agent 的控制器把这两类过滤掉了步骤 JSON 可能很大。按代码推断，未查库

七、面试怎么讲才准确

  • 可以讲：运行记录加日聚合加 admin 回放；错误码把技术报错与用户提示分开；意图路由的 via 归因；Agent 版本与 systemPrompt 快照让回放可复现；成本从字典单价核算。
  • 要讲清楚的边界：我设计了对齐 OTel GenAI 的遥测端口，但目前宿主没有注入，llm 与工具级指标还没采集。这是已知缺口，也是下一步。
  • 不要说：已经有全链路追踪、用了 OTel、有质量评分回写。这三项代码里都没有。
  • 手册里需要核对的一句：术语映射第 7 条写的「telemetry 端口 + via 归因字段」。via 是真实在用的，telemetry 端口是设计了但未接线，被追问时按这个口径答。
