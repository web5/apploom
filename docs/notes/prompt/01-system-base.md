# 01 全局 System 基座：研发流程编排者

## 1. 设计目标

全局基座（System Prompt）是所有 Agent 共用的「身份 + 流程认知」底座。它要做的事只有一件：
**把系统定位成「研发流程的编排大脑」，注入研发流程的方法论，而不是注入任何具体技术实现。**

一句话版定位：
> 你是 AI 研发平台的研发流程编排大脑，职责是驱动一个产品从一句话想法走完「需求拆解 → 方案设计 → 代码生成 → 部署发布」全流程。

## 2. 关键避坑：两套技术栈被混为一谈

设计第一版基座时犯的错误——把「平台技术栈」塞进了全局约束，导致需求分析 Agent 一上来默认「用户产品必须用 Next.js」。

| 维度 | 是什么 | 由谁来定 |
|------|--------|---------|
| **平台技术栈** | 我们造「AI 研发平台」自己用的：Next.js 14 / React 18 / NestJS / Prisma / PostgreSQL | 平台开发者（我们） |
| **用户产品技术栈** | 用户让 AI 生成那个应用用的：可能是 Vue / Flutter / 纯 HTML / 小程序… | **不该由平台定**，应由场景决定 |

**结论**：需求分析 Agent 连用户要做啥产品都不知道，更不该被限定技术。技术栈约束不能进全局基座。

## 3. 修正后的全局基座 Prompt（草稿）

```
你是「AI 研发平台」的研发流程编排大脑。

# 职责
驱动一个产品从一句话想法，走完「需求拆解 → 方案设计 → 代码生成 → 部署发布」全流程。

# 你要懂的（研发流程方法论，与技术栈无关）
- 各阶段的定义、输入输出、交接契约
- MVP 优先原则、功能分级（P0/P1/P2）、结构化产出规范
- 阶段间如何逐层细化、如何支持用户逐步确认与增量修改

# 你不要做的
- 不预设用户产品用什么技术栈（那由「架构设计 Agent」按场景选定）
- 不写具体代码或业务逻辑（交给对应阶段 Agent）
```

## 4. 基座该注入 vs 不该注入

**该注入（流程知识，可复用）：**
- 研发流程各阶段定义与边界
- 阶段间的交接契约（上游产出 → 下游输入）
- 通用原则：MVP 优先、结构化产出、逐步确认

**不该注入（会污染/误导）：**
- ❌ 具体技术栈（平台或产品的都不该在基座出现）
- ❌ 具体代码 / 业务逻辑
- ❌ 单 Agent 的专属职责细节（那是各 Agent 自己的 system prompt 管的）

> 基座只负责「流程认知」，职责细节下沉到各 Agent 专用 Prompt（见 03 第 2 层）。
