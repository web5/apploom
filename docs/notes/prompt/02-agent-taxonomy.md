# 02 Agent 分类：平台能力 vs 业务研发

> 配套：01-system-base.md（基座不预设技术栈）。本篇讲「什么情况下才该绑定技术栈」。

## 1. 核心区分：两类 Agent

设计 Agent 时，必须先分清它**面向谁**：

| 类别 | 面向对象 | 技术栈约束 | 典型例子 |
|------|---------|-----------|---------|
| **平台能力 Agent**（Platform） | 平台**自身**的功能 / 内部业务逻辑 | ✅ 绑定平台技术栈 | 项目管理助手、改平台 UI、计费规则引擎 |
| **业务研发 Agent**（Product） | 用户要造的**那个产品** | ❌ 不绑，由架构设计 Agent 选型 | 需求 / 方案 / 代码 / 部署 四个核心 Agent |

## 2. 本项目的 4 个核心 Agent 全部是 Product 类

设计文档里的主流程四个 Agent，造的都是「用户的产品」，技术栈一概不预设：

| Agent | 类别 | 说明 |
|------|------|------|
| 需求分析 Agent | Product | 连产品是啥都不知道，绝不限定技术 |
| 架构设计 Agent | Product | **它是技术栈的决策者**，自己输出 `techStack` |
| 代码生成 Agent | Product | 读取上游方案的 `techStack`，按它写**用户产品**代码 |
| 部署发布 Agent | Product | 按用户产品的技术栈选构建/部署方式 |

## 3. 技术栈约束的正确归属

```
全局基座          →  完全不出现技术栈
架构设计 Agent    →  自己输出 techStack 字段（按场景选，它是决策者）
代码生成 Agent    →  读取上游 techStack，按它写代码（绑的是「用户产品技术栈」）
平台能力 Agent    →  才在它的 system prompt 里写「你工作在平台内部，技术栈 Next.js/NestJS…」
```

## 4. 何时会出现 Platform 类 Agent

当前阶段（W1-W9）核心是 Product 类 Agent。只有当做「平台自身功能增量修改」时，才用到 Platform 类——
例如 W10 的 AI Runtime 增量修改若用于改**平台后台**，那个 Agent 才绑定 Next.js/NestJS。

> 注意：W10 文档写的「产品自修改」是让用户**生成的产品**内嵌 AI 助手改**用户产品**，本质仍是 Product 视角，不绑平台技术栈。

## 5. 设计 Checklist（写新 Agent 前先过一遍）

- [ ] 这个 Agent 面向「平台自身」还是「用户产品」？→ 定类别
- [ ] 若是 Product 类：它的上游 JSON 契约是什么？技术栈字段由谁给？
- [ ] 若是 Platform 类：才在 prompt 里写平台技术栈
- [ ] 绝不把技术栈写进全局基座
