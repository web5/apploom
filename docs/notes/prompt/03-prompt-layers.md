# 03 四层 Prompt 体系

> 配套：01（基座）、02（Agent 分类）。本篇给整体结构 + 通用技巧。

## 一、四层结构

```
第 1 层  全局 System 基座      → 研发流程编排者定位（见 01）
第 2 层  4 个 Agent 专用 Prompt → 每个 Agent 的角色 + 输入契约 + 输出契约（见 agents/）
第 3 层  增量修改 Prompt        → 对话面板：改已生成产物，复用同一套 schema
第 4 层  通用技巧              → Few-shot / CoT / 约束句（见下）
```

### 第 1 层：全局基座
见 `01-system-base.md`。所有 Agent 共用，只注入流程认知。

### 第 2 层：Agent 专用 Prompt
每个 Agent 一个文件（见 `agents/`）。结构统一为：
```
# 角色        这个 Agent 是谁（含 01 的全局身份前缀）
# 输入契约    上游 JSON（来自上一个 Agent 的产物）
# 输出契约    下游 JSON（严格 Schema，驱动下一个 Agent）
# # 约束      角色单一、MVP 优先、勿输出多余文字
```
**关键**：Agent 之间不直接传自然语言，而是传 JSON Schema 约定的产物。这是编排引擎能串起来的地基。

### 第 3 层：增量修改 Prompt
用户说「把按钮改成蓝色」「加一个导出功能」时调用。
- 输入 = 当前产物 JSON + 用户指令
- 输出 = 修改后的**同一 JSON**（schema 不变）
- 复用第 2 层的输出契约，保证「改完还能接着跑下一步」

### 第 4 层：通用技巧
- **Few-shot**：给 1 个完整产物范例，输出质量立刻稳
- **CoT**：复杂任务（如代码生成）前先让模型列步骤
- **约束句**：`不得输出多余解释文字` 防止污染结构化解析

## 二、四条设计原则（来自避坑指南）

1. **Prompt 先行**：换框架前先优化 Prompt，80% 效果问题出在 Prompt 而非架构
2. **结构化传递**：Agent 间协作靠结构化数据传递，JSON Schema 一定要稳
3. **角色单一**：每个 Agent 只干一件事，避免「既要又要」
4. **逐步确认**：每步产物可被用户对话修改后回填，所以结构要稳定

## 三、落地顺序（写代码前）

1. **先定义 4 套 JSON Schema**（在 `packages/shared`）——这是地基，先于任何 Prompt
2. 写需求分析 Agent 的 Prompt（最简单，先跑通单 Agent）
3. 用流式输出接前端，看到 PRD 实时生成
4. 逐个加 Agent，复用同一套 schema 约定

## 四、Schema 落地的技术约定

- 用 TypeScript 类型 / Zod 在 `packages/shared` 定义契约（见学习计划「技术选型」）
- LLM 输出用 `response_format: json_schema`（OpenAI 兼容接口）或等价约束
- 解析失败要有兜底：重试一次 + 提示模型「严格按 Schema」
