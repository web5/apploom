用 AppLoom 学 AI Agent 开发：高级工程师视角的学习清单

AppLoom 是一条固定阶段的 LLM 流水线 harness（需求 → 原型 → 架构 → 代码生成 → 部署），不是自由规划的 ReAct 式 Agent。它最适合学「把 LLM 当作不可靠组件来做工程化」，这部分与后端和分布式经验高度重合。勾选状态保存在你的浏览器里。

一、可以马上理解的

后端与分布式经验可直接迁移，读代码加看对应测试即可掌握。

二、需要花时间，但这个项目是好教材

读懂不难，建立手感需要亲手跑和改。

三、这个项目学不到的

按通用的 Agent 定义，下面几项需要另找材料补齐。

四、Eval 驱动开发

LLM 应用领域的「测试驱动开发」：先定义「怎样算好」的一组可重复评测，之后每次改 prompt、模型或 harness，都用数字判断变好还是变差。

为什么单测不够用

传统单测LLM 评测
被测对象确定性函数概率性模型，同样输入可能不同输出
判定断言相等，通过或失败统计指标：通过率、一次通过率、成本
回退风险改坏了会红改坏了单测仍全绿（单测用假模型），只有真模型才暴露
一次结果可信要看多用例的整体趋势，单次可能是噪声

例：改了一句 prompt，所有 jest 都绿，但真模型生成代码的构建通过率可能从 4/4 掉到 2/4。只有评测能发现。

在本项目里的闭环

  1. 固定用例集 eval/cases.ts
    4 个典型需求（计数器、待办、书签、静态落地页），由易到难，覆盖有与无 package.json 两条路径。技术栈写死以降低方差。用例 id 不能改，基线按 id 对应。
  2. 真实跑流水线 eval/run-eval.ts
    真模型、真门禁（install、typecheck、build），跑到 codegen 为止，不部署。
  3. 指标汇总 src/eval/metrics.ts
    通过率、一次通过率（无需修复循环即成功）、平均 token、耗时、自动修复次数、门禁修复轮数。
  4. 与基线对比 eval/baselines/*.json
    当前结果对比已保存的基线，找出回退。历史结果在 eval/results/，是改动的数字档案。
  5. 门槛写进工作约定 CLAUDE.md
    改动触及模型调用路径时，pnpm eval 无回退才能提交。

值得学的设计细节

  • 区分环境失败与质量失败。额度用完、鉴权、网络、模型不存在这几类错误标记为 inconclusive，不计入通过率，避免一次 402 被误判成代码变差。
  • 多个指标一起看。通过率没变但 token 翻倍，或一次通过率下降，也是回退：修复循环兜住了质量，成本却上去了。
  • 有预算上限。EVAL_TOTAL_TOKEN_CAP 限制整次评测的 token，超出后剩余用例跳过。
  • 隔离。评测用独立队列 apploom-eval，不与开发 API 抢任务。

典型工作流

发现问题（某类需求总失败）
  → 把它加成一个评测用例（先让评测变红）
  → 改 prompt / harness
  → 跑评测对比基线
  → 目标用例转绿，且其他用例无回退
  → 更新基线，提交

与 TDD 的红、绿、重构同构，区别是「绿」的定义变成统计意义上的不回退，而不是单次断言通过。

局限
  • 用例太少会有方差：4 个用例里一个抖动就是 25% 的波动，必要时同一用例重复跑多次。
  • 只测得到你想到的场景：评测集会过拟合，要把线上真实失败案例持续回灌。
  • 判定方式分层：本项目用「能否构建通过」这种客观判定，成本最低最可靠；文案质量等无法客观判定的场景才需要 LLM-as-judge 或人工打分，可靠性明显更差。
  • 每次都花钱：所以便宜的单测每次跑，评测只在改动模型路径时跑。

五、建议的学习顺序

这里的先后顺序有意义，前一步是后一步的前提。
