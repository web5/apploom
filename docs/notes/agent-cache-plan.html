web_system 的 Agent 缓存接入方案

目标是提升 Agent 的性能和稳定性。先说清一个前提：缓存主要省时间和成本，对准确率只有间接帮助，设计不好反而会降低准确率。本文给出分层方案、准入规则、实现位置和验证方式，并标出我实测过和没有验证的部分。这是设计文档，没有改动任何业务代码。

一、结论摘要

  • 可以做，建议分五层逐步上，第一步只做 L0：记录网关返回的 cached_tokens 并稳定提示词前缀，半天完成，没有行为风险。
  • 网关已经支持提示词前缀缓存（我实测，见第二节），但现有代码没有读这个字段，所以目前看不到命中情况。
  • 缓存与准确率：能提升一致性；但缓存过期数据、失败结果、相近但不同的问题，会直接降低准确率。所以要有准入规则，且工具缓存默认关闭、逐个显式开启。
  • 是否值得做 L1 以后各层，取决于真实流量的重复率，目前没有数据。先打点再决定。

网关前缀缓存实测

对 TokenHub 的 deepseek-v4-flash 连续发 3 次请求，系统提示词相同（约 7060 token），只有最后一句用户问题不同：

第 1 次706000%2.09 秒

  • 已确认：网关支持提示词前缀缓存，并在响应的 prompt_tokens_details.cached_tokens 里返回命中数。
  • 没有得出的结论：延迟收益。样本只有 3 次，且 max_tokens=8 时推理 token 占满预算（finish_reason=length），耗时被推理干扰。
  • 没有核实：缓存 token 是否按更低价格计费；其他模型是否也返回这个字段。
  • 顺带复现了你们之前的空输出问题：小预算加推理模型会把输出预算耗尽。

三、分层方案

层缓存什么缓存键收益风险
L0 提示词前缀不自建缓存，利用网关的前缀缓存前缀字节完全一致省输入 token 成本，可能降首包延迟几乎没有。历史摘要变化后前缀会断
L1 意图分类分类结果（目标助手加置信度）规范化 query、候选助手集合版本、提示词版本、模型 id路由一致，省一次 LLM 调用命中率未知；候选集合变化要失效
L2 只读工具结果工具调用返回工具名、规范化参数、用户或租户范围、数据版本省工具耗时，减少重复调用过期读、串用户，见第四节
L3 检索与向量查询向量、分块向量、召回结果文本内容哈希加 embedding 模型名省 embedding 成本和时间低；语料变了哈希自然变化
L4 语义缓存相似问题的最终答案问题向量加相似度阈值加用户范围FAQ 类助手收益大最高：相似不等于相同

L0：具体怎么做

  1. 在 tokenhub.client.ts 解析 prompt_tokens_details.cached_tokens，放进 usage。
  2. 在遥测的 onLlmSpan 事件里增加 cachedTokens，后台可以统计命中比例。
  3. 检查各 Agent 的提示词前缀是否稳定：系统提示词里有没有时间、随机数、用户名；技能目录和工具 schema 的顺序是否确定。
  4. 把变化频繁的内容尽量放到最后。当前引擎的顺序里，历史摘要在压缩后会变化，之后的前缀就失效，这是预期内的代价。

我在搜索范围内没有发现日期注入，但没有读完 ai-agent 全部提示词拼装代码，不排除别处有动态内容。

L1：意图分类缓存

  • 只缓存 via 为 llm 的结果。规则命中的本来就是零 LLM 开销，不需要缓存。
  • 置信度低于阈值走兜底的结果不缓存，避免把「没把握」固化。
  • TTL 建议从几分钟起步，候选助手集合或分类提示词变更时按版本号失效。
  • 上线前先用日志统计「重复 query 占比」，占比很低就不做。

L2：工具结果缓存

在工具契约里增加声明，默认不缓存：

interface ToolCachePolicy {
  /** 默认 false。只有显式声明才缓存 */
  enabled: boolean;
  ttlMs: number;
  /** 参与缓存键的参数字段；其余参数变化不影响命中 */
  keyFields: string[];
  /** user：按用户隔离；tenant：按租户；global：仅限无用户数据的公共结果 */

  versionOf?: string;
}
工具类别是否缓存说明
read-file、grep-search、list-dir可以，短 TTL键里带文件修改时间或内容哈希更稳妥
list_modules可以，较长 TTL模块列表变化很少
get_current_versions、list_releases不建议，或绑定发布事件失效部署 Agent 的门禁要求版本号必须来自工具返回，过期值会让 Agent 基于旧版本做判断
get_job_status绝不缓存轮询要拿最新状态，缓存会让轮询永远不到终态
publish_pipeline、publish_version、rollback、promote_release、cancel_job绝不缓存有副作用的操作
web 搜索可以，短 TTL时效性内容 TTL 要更短

工具清单取自部署助手的工具列表与 agent-core 的 coding 工具；各工具是否真有副作用，实施前要逐个确认。

四、缓存与准确率的关系

能间接提升的

  • 相同输入得到相同的路由或检索结果，减少随机波动。
  • 把已验证的结果固定下来，避免「今天对明天错」。

会降低准确率的，也是设计的重点

  • 缓存过期数据。例如缓存了 get_current_versions，发布完成后 Agent 仍告诉用户旧版本。
  • 缓存了失败结果。你们遇到的空输出问题：如果把 finish=length 且内容为空的响应缓存下来，故障会被钉死。
  • 语义缓存误命中。「发布到 dev」和「发布到 prod」语义相近，错误命中的后果严重。
  • 串用户数据。缓存键没带用户或租户，会把一个人的结果给另一个人。
  • 缓存污染。提示词注入让模型产出恶意内容，被缓存后影响后续请求。

准入规则（写进缓存层，而不是靠自觉）

  1. LLM 结果：只缓存 finish_reason=stop、内容非空、通过 schema 校验的响应。
  2. 工具结果：只缓存成功且未被截断的结果；失败、超时、部分结果一律不缓存。
  3. 缓存键必须包含范围字段（用户或租户），默认按用户隔离。
  4. 工具缓存默认关闭，由工具作者显式声明 TTL 和键字段。
  5. 带副作用的工具在代码层面禁止开启缓存，而不是文档约定。
  6. 每次命中都要在遥测里记录来源，便于排查「这个答案是不是缓存的」。

六、验证方式

  1. 先打点再决策：L0 上线后看一周的前缀命中率；用日志统计 L1 的重复 query 占比。
  2. 用评测防回退：
    • 部署轨迹评测（llm-bench 的 src/traj）：开关缓存前后，6 条门禁的违规率不能上升。
    • 新增过期读场景：发布完成后再问当前版本，缓存开启时 Agent 不能报出旧版本。这个场景要先写、先让它在有缺陷的缓存上变红，再修。
    • RAG 评测：开启检索缓存前后，命中率与拒答表现不能变。
  3. 灰度：工具缓存逐个工具开启，监控过期读和用户投诉。
  4. 语义缓存：只有在评测里证明误命中率足够低，才对 FAQ 类助手开启，带工具的助手不做。

九、面试可讲的点

  • 缓存不是越多越好：我先实测了网关是否暴露命中信息，再设计分层，而不是直接上语义缓存。
  • 缓存与准确率的取舍：准入规则、默认关闭、副作用工具代码层禁止，对应的是你们 get_job_status 与版本真实门禁。
  • 空输出问题和缓存的关联：不缓存失败结果，否则会钉死故障。
  • 诚实口径：这是设计与实测，还没有落地；落地前先打点。

十、问题相同，但业务数据会变：怎么缓存

核心原则：问题相同不等于输入相同。缓存键要由真正决定答案的全部输入生成，其中包括业务数据本身。这样数据一变，缓存自动未命中，新鲜度由构造保证，而不是靠失效逻辑不出错。

主方案：数据实时取，缓存「基于数据生成答案」这一步

  1. 决策步骤（调用哪个工具）：可缓存。键为规范化问题、工具 schema 版本、提示词版本、模型 id。
  2. 取数步骤（工具执行）：实时执行，不缓存。读取数据通常又快又便宜。
  3. 生成步骤（基于工具结果写回答）：可缓存。键为完整消息的哈希，其中已包含刚取到的数据。数据不变则命中，数据变了哈希变化，自动未命中。

省下的是最贵的 LLM 调用，数据始终是新的。多步 Agent 循环里每一步的输入都包含前面所有工具结果，所以任何一步的数据变化都会让后续各步自动失效。

必须守住的规则

  • 不缓存带副作用的决策。输出里包含对写工具的调用时，这一步整体不进缓存。
  • 缓存键必须带用户或租户范围。同一句话，不同用户看到的数据不同。
  • 含时间敏感词的问题不缓存。例如「今天」「刚刚」「最新」「现在」。回答里若含相对时间，也不应缓存。
  • 工具结果里的时间戳、请求 id 会让哈希永远不同。只能剔除已确认不影响答案的字段，剔除过多又会造成误命中，需要逐个工具评估。
  • 参与缓存的调用温度设为 0。否则缓存只是钉住了一次随机采样。
  • 失败、空输出、截断的响应不缓存（见第四节准入规则）。

验证

  1. 在轨迹评测里增加「数据变更后再问」场景：先问一次，修改 mock 后端里的版本，再问一次，回答必须反映新版本。现有 mock 后端已有版本与作业状态机，可以扩展。
  2. 统计过期读事件：命中缓存但回答与实时数据不一致的次数，目标为零。
  3. 对比开关缓存前后，门禁违规率和回答准确率都不能下降，再看节省了多少 LLM 调用和 token。

未核实：内容中心、知识库等服务是否有可靠的版本号或更新时间，我没有读它们的代码。版本号做缓存键的方案，只在这个前提成立时适用。
